GSW-Ti — global service

00개요 Overview

GSW-Ti는 현대자동차와 기아의 글로벌 서비스 사이트를 통합하고, 국가·지역별로 흩어져 운영되던 서비스 정보와 업무 프로세스를 표준화하는 프로젝트였습니다. 각 지역의 운영 환경을 고려하면서도 글로벌 공통으로 쓸 수 있는 서비스 체계를 만드는 것이 목표였습니다.

서비스 기획자로 참여해 기존 서비스 분석부터 통합 정보 구조(IA) 설계, 기능 정의, UI/UX 기획, 화면 상세 명세까지 기획 전반을 맡았습니다.

01문제 정의 Problem

같은 목적의 서비스가 지역과 브랜드마다 따로 운영되고 있었고, 비슷해 보여도 운영 정책은 서로 달랐습니다.

  • 분산된 구조. 지역별 서비스 사이트를 분석해 보니 메뉴 구성, 기능, 운영 방식이 서비스마다 달랐습니다.
  • 같은 듯 다른 브랜드. 현대자동차와 기아는 서비스 목적은 비슷하지만 세부 운영 정책에 차이가 있었습니다. 그래서 모든 기능을 동일하게 통합할 수는 없었습니다.
  • 화면만으로 정의할 수 없는 기능. TSB(Technical Service Bulletin)는 단순한 게시판이 아니라 승인, 배포, 권한, 상태 관리가 복합적으로 얽힌 업무였습니다.

02의사결정 Decision

결정 01
모든 기능을 똑같이 통합하지 않고, 공통 정책과 브랜드별 정책을 나눈다
근거
서비스 통합은 UI를 똑같이 만드는 일이 아니라, 서로 다른 업무 체계를 분석하고 적절한 기준으로 표준화하는 일이라고 보았습니다. As-Is 분석에서 공통 기능과 차별화 기능을 먼저 구분했습니다.
결정 02
공통으로 쓰는 화면은 컴포넌트와 게시판 양식으로 먼저 표준화한다
근거
글로벌 사용자에게 일관된 경험을 주려면 공통 기준이 먼저 있어야 합니다. 다만 개별 메뉴의 특성은 유지할 수 있도록, 공통 패턴 위에 메뉴별 UI를 설계했습니다.
결정 03
TSB는 화면보다 업무 규칙과 상태값을 먼저 정의한다
근거
상태에 따라 사용자가 할 수 있는 작업과 보이는 버튼이 달라지는 구조였습니다. 업무 규칙과 프로세스가 정리되지 않으면 화면을 설계할 수 없었습니다.
결정 04
사용자뿐 아니라 운영하는 관리자의 관점까지 함께 설계한다
근거
현업·유관 부서와 협의하며 실제 운영 환경을 파악했고, 그 내용을 기능과 정책으로 구체화하려면 시스템을 쓰는 사용자와 서비스를 운영하는 관리자의 관점을 함께 봐야 했습니다.

03실행 Execution

  • As-Is → To-Be 구조 설계. 지역별 서비스의 메뉴·기능 구조를 파악하고 공통 기능과 차별화 기능을 구분해, 글로벌 통합 메뉴 구조와 전체 IA를 세웠습니다.
  • 공통 UI 표준화. 공통 UI 컴포넌트, 게시판 공통 양식과 화면 구성을 정의하고, 공통 기능과 화면 패턴을 표준화했습니다.
  • KEY/PIN. 메인·사용자 관리 화면, 관리자 기능, 사용 이력 관리, API Key 관련 기능을 정의했습니다.
  • TSB. 기술 정보 게시·관리 기능, 승인·게시 프로세스, 지역별 승인 체계, 사용자별 권한, 상태값에 따른 버튼·기능 제어를 정의하고 현대자동차와 기아의 운영 정책 차이를 반영했습니다.
  • Admin·Login. 운영을 위한 관리자 기능을 설계하고, 글로벌 사용자 회원가입·이메일 인증 정책과 PIC 사용자의 최초 로그인 프로세스를 검토했습니다.
  • 화면 상세 명세. 사용자 시나리오와 업무 흐름, 기능별 동작, 권한과 접근 범위, 버튼·상태값별 동작을 정리해 화면별 상세 명세서를 작성했습니다.

PC에서만 하던 정비 업무를 태블릿으로 옮길 때, 무엇이 빠지면 안 되는가?

Role

Period
[기간 추가 필요]
Scope
업무 프로세스 검증, 화면설계서, QA·통합테스트, 문서화, 현장 교육
Collaboration
개발팀, QA [팀 구성 추가 필요]

00개요 Overview

정비사가 PC에서만 처리할 수 있던 정비 업무를 태블릿에서도 쉽게 처리할 수 있도록 정비 모바일 앱을 구축하는 프로젝트였습니다. 정비 현장에서 바로 업무를 처리하게 하면서도, 기존 업무 프로세스가 모바일에서 정확하게 이어지게 하는 것이 목표였습니다.

저는 서비스 기획자로 업무 프로세스 검증, 화면설계서 현행화, 개발·QA 커뮤니케이션, 통합테스트, 현장 사용자 교육까지 기획부터 현장 적용까지 맡았습니다.

01문제 정의 Problem

이 프로젝트의 위험은 화면이 아니라 흐름에 있었습니다. PC 업무가 모바일로 옮겨지는 과정에서 단계 하나가 빠지거나 달라지면, 현장에서는 업무 자체가 끊깁니다.

  • 기획·개발 간 흐름 불일치. ADM 기획 리뷰에서 정비 업무별 프로세스를 다시 짚어 보니, 기획과 개발이 정의한 업무 흐름에 잘못 정의된 부분이 있었습니다.
  • 도메인 이해 격차. 정비 업무는 용어와 절차가 전문적이어서 구성원마다 이해 수준이 달랐고, 이 차이가 커뮤니케이션 비용으로 이어질 수 있었습니다.
  • 문서로는 보이지 않는 오류. 일부 기획 오류는 설계서가 아니라 실제 흐름을 돌려 보는 통합테스트에서야 드러났습니다.

02의사결정 Decision

결정 01
화면 설계보다 업무 흐름 검증을 먼저 한다
근거
PC 업무를 모바일로 옮기는 프로젝트에서는 화면 구성보다 업무 흐름이 그대로 이어지는지가 더 중요했습니다. 실제 업무 순서와 규칙을 모르면 화면을 제대로 설계할 수 없습니다.
결정 02
화면설계서를 ‘계속 갱신하는 기준’으로 운영한다
근거
잘못된 프로세스가 발견되고 수정되는 일이 반복되었습니다. 설계서가 한 번 쓰고 끝나면 개발과 QA는 서로 다른 버전을 보게 됩니다.
결정 03
도메인 지식을 개인이 아닌 팀 문서로 남긴다
근거
구성원 간 이해 수준 차이가 그대로 커뮤니케이션 비용이 됩니다. 한 사람이 아는 지식을 문서로 만들면 팀 전체의 이해도가 같이 올라갑니다.
결정 04
설계서 전달에서 멈추지 않고 테스트와 현장까지 간다
근거
문서만으로는 찾을 수 없는 오류가 있고, 실제 사용 환경의 어려움은 현장에서만 보입니다.

03실행 Execution

  • ADM 기획 리뷰. 정비 업무별 프로세스를 재확인하고 기획·개발 간 흐름 정합성을 검토한 뒤, 결과를 정리해 개발자에게 공유했습니다.
  • 설계서 현행화. 잘못 정의된 업무 프로세스를 바로잡고 화면설계서에 반영해, 개발팀이 항상 최신 기준으로 개발하도록 공유했습니다.
  • QA 지원. QA 담당자가 정비 업무와 기획 의도를 이해하고 테스트할 수 있도록 문의에 대응하고 설명 자료를 작성했습니다.
  • 통합테스트 참여. 실제 흐름에서 드러나는 기획 오류를 직접 찾아 수정했습니다.
  • Confluence 문서화. 전체 업무 프로세스와 정비 용어·절차를 정리해 누구나 참고할 수 있게 했습니다.
  • 현장 교육. 정비사분들이 어려움 없이 앱을 쓸 수 있도록 현장에서 사용 교육을 지원하고, 실사용 과정을 직접 확인했습니다.

Dealer365 — Sales

디자이너·개발자·기획자가 같은 화면을 서로 다르게 읽는다면?

Role
인벤티스 서비스기획팀 (수습기간 당시 소속)
Period
2025.03.24 — 2025.05.23
(수습기간 1–8주차)
Module
Sales, CRM, Configurator
Collaboration
디자인팀, 베트남 개발팀, 콘텐츠팀

Figma (Annotation), Jira

00개요 Overview

자동차 딜러가 사용하는 서비스 Dealer365에 실무 기획자로 참여해 사용자 관점의 기획, 기능 정의, 화면설계를 진행했습니다. 디자인팀, 콘텐츠팀, 베트남 개발팀과 함께 일하는 구조였습니다. [서비스 전체 개요 추가 필요]

서비스 전체 IA, 고객 여정 기반 차량 구매 플로우와 Car Detail 기획, CRM 기능·상태 정의, 페이지 리스트와 화면설계서 기준 수립, Animation Transition 가이드, Configurator QA, 딜러 현장 리서치를 맡았습니다.

01문제 정의 Problem

여러 팀이, 그것도 해외 개발팀과 함께 일하는데 모두가 같이 보는 기준이 없었습니다.

  • 반복되는 피드백. Car Detail 기획을 마친 뒤에도 피드백이 반복해서 들어오며 기획 일정이 지연되고 전체 진행 속도가 느려졌습니다.
  • 기능 위치와 흐름의 혼선. 페이지·팝업을 부르는 공통 이름과 진입 경로가 정리되지 않아 협업 중 혼선이 생길 수 있었습니다.
  • 디자인과 개발의 해석 차이. 기능 기준이 문서화되지 않으면 같은 화면을 서로 다르게 해석하게 됩니다.
  • 정의되지 않은 영역. 화면 전환(Transition) 애니메이션은 구현 범위가 불분명했습니다.
  • 제한된 디자인 리소스. 디자인팀 리소스가 부족해 일정 지연이 우려되는 상황이었습니다.

02의사결정 Decision

결정 01
리뷰를 여러 번 돌리지 않고, 핵심을 미리 정리해 한 번에 확정한다
상황
기획을 마친 뒤에도 피드백이 반복적으로 발생하면서 기획 일정이 지연되고 전체 진행 속도가 느려지고 있었습니다.
실행
부장님과 함께 Car Detail 페이지에 필요한 데이터를 공통 언어로 리스트업하고 카테고리로 묶었습니다. 한 번의 피드백으로 끝낼 수 있도록 핵심만 사전 정리해 대표님·부장님과 방향을 먼저 확인했고, 탭 버튼 형식의 인터페이스 예시를 함께 제시해 실제 사용 시나리오를 기준으로 이해와 공감을 얻었습니다. 이후 각 팀장님들과 1회 리뷰로 수정·확정했습니다.
결과
반복 피드백 없이 기획을 마무리하고, 디자인팀에 와이어프레임을 원활히 인계했습니다.
결정 02
모든 화면에 UserFlow 순서를 따르는 ID를 붙인다
근거
화면별 ID가 있어야 추적과 문서 관리가 쉬워지고, 사용자 흐름 순서로 번호를 매기면 ID만 봐도 내비게이션 구조가 보입니다. 개발자·디자이너가 같은 화면을 같은 이름으로 부를 수 있습니다.
예시
UI_SA_002_001_1 = Sales 모듈 · New Vehicle 첫 화면 · 내부 필터 팝업
결정 03
설계서 하나를 쓰기 전에 템플릿과 작성 가이드부터 만든다
근거
일관된 작성 기준이 있어야 팀원 간 이해도가 오르고 재사용할 수 있습니다. 설계 의도를 기록으로 남겨, 프로젝트 이후에도 기능이 왜 이렇게 만들어졌는지 확인할 수 있게 했습니다.
결정 04
디자인 리소스 공백은 기획자가 직접 채우되, 디자인 시스템 규칙 안에서
근거
일정 지연이 우려되는 상황에서 빠르게 의사결정해 마감 안에 결과물을 내는 것이 우선이었습니다. 동시에 디자인 가이드의 의도를 훼손하지 않도록 기존 컴포넌트·레이아웃·간격 규칙을 분석해 따랐습니다.
결정 05
전환 애니메이션의 범위를 Configurator 공통 컴포넌트로 좁혀 정의한다
근거
구현 범위가 불분명한 영역은 기획자가 범위부터 명시해야 개발자가 일관되게 구현할 수 있습니다. M3 Design System의 Transition Pattern을 기준으로 삼았습니다.
결정 06
QA는 ‘기능이 구현됐는가’가 아니라 ‘실제로 쓸 수 있는가’로 본다
근거
릴리스 전에 사용자 관점의 흐름을 점검해야 오류를 일찍 찾을 수 있습니다. QA 중 발견한 문제 중 일부는 기획 정의가 부족했던 경우여서, 기획 문서 보완이 필요한지도 함께 판단했습니다.

03실행 Execution

  • IA와 Car Detail. 서비스 전체 IA를 설계하고, 차량 구매 고객의 여정을 케이스별로 설계·분석했습니다. Car Detail에 들어갈 필수 데이터를 리스트업·카테고리화하고 레퍼런스를 조사해 카테고리별 와이어프레임을 만들었습니다.
  • CRM. HubSpot을 분석해 CRM 기능과 상태를 정의하고, 엔티티별 ERD와 Contacts·Deals 와이어프레임을 만들어 리뷰했습니다.
  • Page List 정리. 기능 대분류 정렬 → 묶음별 번호 → UserFlow 순서대로 ID 부여 → 페이지 유형 보조 적용. 페이지 ID명 정의, 중복 페이지 경로 파악, 페이지/모달 기준 정의, 화면별 설명과 진입 경로를 함께 정리했습니다.
  • Sales Layout 화면설계서. GNB·LNB·필터·리스트를 기능 단위로 나눠 넘버링하고, 상단 → 필터 → 리스트 → 상세 진입의 탐색 흐름 순서로 배치했습니다. 컴포넌트별 ID·기능·조건, EV 뱃지 같은 조건부 노출 로직, 클릭 시 이동 흐름까지 명시했습니다.

수업과 실험으로 약속 잡기 어려운 학생들은 어떻게 거래해야 할까?

Role
UX/UI 기획 및 디자인
Period
2023.05 — 2024.02
Program

Collaboration
PM, 프론트엔드·백엔드 개발자

00개요 Overview

과학기술원은 지리적 특성상 교외에서 중고거래를 하기 어렵습니다. 학생들은 개강 전 2–3일 동안 한시적인 오프라인 중고장터를 열었지만, 정해진 시간과 장소에서만 열리다 보니 접근성이 낮았습니다.

UX/UI 디자이너로 참여해 서비스 플로우 기획과 화면·디자인 시스템을 맡았고, PM과 기획 요소를 논의하며 개발자와 구현 난이도를 조율했습니다.

01문제 정의 Problem

학생들은 이미 해결책을 쓰고 있었습니다. 바쁜 일정 때문에 특정 장소에 물건을 두고 찾아가는 방식으로 거래를 시도하고 있었던 것입니다.

  • 약속 잡기가 가장 큰 장벽. 수업과 실험 일정이 바빠 대면 거래 약속을 잡기 어려웠습니다.
  • 상시 거래 창구의 부재. 오프라인 장터는 기간이 정해져 있어 일정이 안 맞으면 이용할 수 없었고, 물품 리스트도 정리되어 있지 않았습니다.
  • 운영 부담과 신뢰 문제. 남은 물건 관리와 거래 중 분쟁 조정이 운영 측의 부담이었고, 기존 중고거래 플랫폼에는 학교 내 거래 환경에 맞춘 기능이 없었습니다.

02의사결정 Decision

결정 01
사물함 거래를 서비스의 핵심 기능으로 만든다
근거
학생들이 이미 하던 ‘두고 찾아가기’ 행동을 정식 거래 방식으로 옮기면, 대면 약속 없이도 물건을 교환할 수 있습니다.
결정 02
그래도 직접거래로 바로 바꿀 수 있는 경로는 남긴다
근거
빈 사물함이 없거나, 막상 물건을 직접 보고 싶은 상황이 생깁니다. 한 가지 방식만 강요하면 거래가 멈춥니다.
결정 03
가입은 GIST 학부생으로 제한하되, 단계는 최소화한다
근거
비대면 거래일수록 상대에 대한 신뢰가 중요합니다. 학교 이메일 인증만으로 가입을 끝내 신뢰와 편의를 함께 챙겼습니다.
결정 04
일정 조율을 채팅 이전, 상품 등록 단계로 앞당긴다
근거
판매자가 등록할 때 거래 희망 시간과 장소를 미리 입력하면, 서로 일정을 맞추는 사전 조율 과정이 줄어듭니다.
결정 05
핵심 기능에 집중하고, 구현이 어려운 부분은 대안으로 절충한다
근거
사용자에게 중요한 정보와 기능의 우선순위를 먼저 구별했습니다. 개발이 어려운 디자인은 이유를 묻고, 설득력이 있으면 디자인으로 해결할 대안 옵션을 가져와 콘셉트와 개발 일정을 함께 지켰습니다.

03실행 Execution

  • 캐비(사물함) 거래 플로우. 판매자가 사물함을 선택하고 비밀번호 설정, 보관 사진 촬영을 마치면 구매자에게 정보가 전달되어 원하는 시간에 찾아갑니다. 채팅 중에도 직접거래로 바로 전환할 수 있습니다.
  • 신뢰 장치. 학교 이메일 인증 가입, 판매자의 역대 거래 물품·거래 후기·신뢰 평점 노출.
  • 빠른 탐색. 키워드 알림, 추천 태그, ‘우리 학과 단골 거래상품’ 같은 큐레이션 메뉴, 사물함 거래 가능 상품 태그.
  • 최소 입력 등록. 사진·카테고리 기반 AI 가격 추천, 거래 방식 추천, 거래 희망 시간·장소 사전 입력.
  • 사용성 테스트. 거래 상황별 베타테스터 8명의 화면 녹화와 인터뷰로 플로우별 피드백을 정리하고, 버그·이슈를 정식 런칭 전에 해결했습니다.
일정 맞추기 어려운 경우에도 사물함에 물건을 보관하고, 상대방이 편한 시간에 찾아갈 수 있어서 시간 절약이 됐어요.베타테스터 · 캐비거래 FLOW

정식 런칭 후 1개월 기준 데이터입니다. 사물함 거래 비중을 보면 판단 01이 실제 거래 방식으로 자리 잡았음을 알 수 있습니다.

00개요 Overview

MZ세대는 숏폼으로 트렌드를 접하고, 소비하는 동시에 직접 만들기도 합니다. 한입폼은 숏폼 크리에이터의 콘텐츠 제작을 돕는 생성형 AI 대본 플랫폼으로, 클로바 스튜디오를 활용해 한국의 최신 트렌드를 반영하도록 설계했습니다.

모바일 웹 UX/UI 디자인을 맡아 사용자 리서치, 유저 플로우, 화면 디자인, 사용성 테스트 기반 개선을 진행했습니다. [프롬프트 설계 참여 범위 등 세부 역할 추가 필요]

01문제 정의 Problem

크리에이터의 병목은 촬영이나 편집보다 그 앞, 무엇을 어떻게 말할지 정하는 기획 단계에 있었습니다.

  • 리서치. 숏폼 크리에이터 96명 온라인 설문과 4명 심층 인터뷰를 진행했습니다.
  • 아이디어 고갈. 내 채널 주제에 맞는 트렌디한 아이디어를 지속적으로 찾기 어려웠습니다.
  • 대본 작성 시간. 주제와 트렌드, 채널만의 말투와 분위기까지 고려하다 보니 스크립트 작성이 오래 걸렸습니다.
  • 범용 AI의 한계. 범용 생성형 AI는 트렌드에 맞지 않는 형식적인 답변을 줘서 잘 쓰지 않는다는 응답이 있었습니다.
GPT를 써서 빠르게 만들고 싶은데 트렌드에 안 맞는 형식적인 답변만 줘서 잘 사용하지 않아요.인터뷰 · 20대 유튜버

02의사결정 Decision

결정 01
서비스 범위를 ‘아이디어 → 대본’ 기획 단계로 좁힌다
근거
크리에이터들이 가장 어려움을 겪는 지점이 기획이었습니다. 목표를 ‘크리에이터의 콘텐츠 생성 시간을 최대한 줄이는 것’으로 정했습니다.
결정 02
필요한 내용만 단계별로 입력하면 대본이 나오게 한다
근거
크리에이터가 기획에 쓰는 시간을 줄이는 것이 목표였기 때문에, 필요한 내용만 입력하면 트렌디한 스크립트가 나오도록 입력을 채널 소개 → 필수 내용 → 길이·말투 순서로 나눠 프롬프트를 구성했습니다.
결정 03
말투·사투리·유행어를 선택지로 제공한다
근거
인터뷰에서 크리에이터들은 채널만의 말투와 분위기를 대본에 녹이는 데 많은 신경을 쓴다고 답했습니다. 트렌드 문구도 직접 고를 수 있어야 했습니다.
결정 04
온보딩은 건너뛰지 못하게, 끝까지 보도록 유도한다
근거
Maze 사용성 테스트에서 온보딩 캐러셀 Mis-Click이 38%였고, 온보딩을 보지 않고 대본을 만들다 서비스를 이해하지 못한 채 이탈하는 경우가 있었습니다.

03실행 Execution

  • 4단계 플로우. ① 아이디어 생성(채널 소개·카테고리·영상 소개) ② 필수 내용, 인트로·엔딩 문구 ③ 영상 길이, 존댓말·사투리·유행어 ④ 스크립트 생성.
  • 결과 화면. 프로그레스바로 생성 진행을 보여주고, 북마크·복사·공유를 제공했습니다. 제작 팁과 유사 아이디어는 아코디언으로 묶어 화면이 지나치게 길어지지 않게 했습니다.
  • 온보딩 개선. 클릭형 캐러셀을 ‘다음’ 버튼 흐름으로 바꾸고, 상세 설명을 추가하고, 버튼 색상과 문구를 바꿔 대본을 쓸 준비가 되었음을 알렸습니다.

04성과 Result

  • 타겟 유저 피드백에서 “소재가 참신하다”, “스크립트와 아이디어까지 제시해줘 도움이 된다” 등 긍정적인 반응

00개요 Overview

국내 외국인 유학생이 늘면서 대학 입학·졸업·취업에 필요한 TOPIK(한국어능력시험) 응시자와 TOPIK 교육에 대한 니즈도 함께 커지고 있습니다(데스크 리서치).

리서치와 페르소나 정의, 앱 UX/UI, 그리고 네이밍·로고·캐릭터를 포함한 BX 디자인을 진행했습니다. [팀 내 세부 역할 확인 필요]

01문제 정의 Problem

학습자는 “풀고 끝나니까 이게 진짜 도움이 되는 걸까?”라고 느끼고 있었습니다.

  • 경쟁 앱 분석. 기존 TOPIK 앱은 단순 문제 풀이에 집중해 학습 진행 추적과 정확한 피드백이 부족했고, 체계적인 쓰기 첨삭 기능이 없었습니다.
  • 사용자 인터뷰 (TOPIK 유경험자 4명). 한국어 이해도에 따라 어려워하는 유형이 달랐고, 부족한 부분에만 집중하고 싶어 했습니다. 얼마나 풀었는지 눈에 보일 때 동기부여가 된다는 응답이 있었습니다.

02의사결정 Decision

결정 01
목표 급수에 따라 사용자를 둘로 나누고, 기능을 다르게 준다
근거
3·4급 준비생은 유형별 전략과 실전 문제 풀이가, 5·6급 준비생은 쓰기 피드백과 시간 관리가 과제였습니다. 하나의 학습 흐름으로는 두 사람 모두를 만족시킬 수 없었습니다.
결정 02
쓰기는 원고지 형태로, 실전과 같은 환경에서 연습하게 한다
근거
TOPIK 쓰기는 띄어쓰기가 중요한 문제입니다. 실전과 비슷한 입력 환경이어야 연습이 시험으로 이어집니다.
결정 03
학습량과 성과를 홈 화면에서 바로 보이게 한다
근거
인터뷰에서 목표 설정과 눈에 보이는 성과가 동기부여 요인으로 꼽혔습니다.

03실행 Execution

  • 맞춤형 온보딩과 홈. 한국어 수준·목표 급수·공부 목적을 받아 홈을 구성하고, 목표 급수·출석·학습 시간 배너와 오늘의 단어 카드를 제공했습니다.
  • 3·4급 — 유형 학습. 급수와 목표에 맞춘 ‘오늘의 유형 문제 코스’, 유형별 섹션, 북마크, 문제별 상세 해설.
  • 5·6급 — AI 모의고사 분석. 실전 타이머, 영역별 평균 점수 분석과 예상 급수, 복습할 취약 유형 제안.
  • 쓰기 솔루션. 원고지 입력 UI, AI 첨삭·모범 답안·추천 동의어·연관 어휘.
  • 브랜드. TOPIK + KEY = TOPIKI. 토끼 귀 한쪽을 열쇠 형태로 디자인해 ‘학습의 열쇠’와 ‘도약’을 결합했습니다.
